# HLS m4v 구간 다운로드 추가 진단

## 요청과 범위

사용자가 제공한 `range-d2ad7f0a9a6f4351ac3749fa9fcf7872.part.log`를 읽고 이전 HTTPS 수정 후에도 구간 다운로드가 중단되는 원인을 점검했다. 이번 작업은 진단과 합성 자료 재현이다. 앱 소스 수정·빌드·배포는 하지 않았으며 사용자 영상·채팅·모델·분석 결과와 첨부 로그는 변경하지 않았다.

첨부 로그에는 유효기간과 서명 값이 들어간 CDN URL이 있어 이 문서나 재현 자료에 복사하지 않았다. 실제 사용자 URL로 추가 다운로드를 실행하지 않았다. 로그에 실행 파일 경로·FFmpeg 버전은 없으므로 사용자가 실행한 앱 버전 자체는 이 파일만으로 확정할 수 없다.

## 확인한 원인

로그는 HTTPS 조각 열기 → 내부 형식 `mov,mp4,m4a,3gp,3g2,mj2` 감지 → `.m4v` 파일명과 허용 형식 확장자가 맞지 않아 거부 → 첫 세그먼트 로딩 실패 → `Invalid data found when processing input` 종료 순서다.

핵심 메시지는 `mismatches allowed extensions`와 `Error when loading first segment`다. 앞선 `Protocol not found` 오류와 다르며 이번 로그는 메모리·저장 공간 부족이나 인증서 오류를 가리키지 않는다. `Invalid data`라는 최종 메시지만으로 원본이 손상됐다고 판단할 수 없다.

현재 배포의 FFmpeg 8.1.3 소스에서 HLS 세그먼트 검사는 두 번 이루어진다.

1. HLS 허용 확장자에는 `m4v`가 있어 통과한다.
2. 실제 감지한 MP4 컨테이너의 확장자 및 HLS 별칭 목록에는 `m4v`가 없어 거부한다.

이는 Windows 전용 코드가 아니며 동일 소스를 사용하는 macOS에도 영향을 준다. 근거는 [배포에 사용한 FFmpeg 커밋의 hls.c](https://github.com/FFmpeg/FFmpeg/blob/1041abdc962f4cc4f394aa8de9dc5236c0c3b9e7/libavformat/hls.c)의 `test_segment`, `allowed_segment_extensions`, `extension_picky`와 `libavformat/mov.c`의 입력 확장자 목록이다.

## 실제 배포 바이너리 재현

`v0.20.0-preview.6` macOS ZIP에서 FFmpeg·ffprobe만 별도 검사 폴더로 추출했다. FFmpeg SHA-256은 기존 패키지 검사 기록과 같은 `06a8e8248ed0281b15cb06c87dd295325af46dbcff9d3885b0043041ee2243e5`다.

공개 합성 4초 영상을 초기화 조각 `init.m4s`와 fMP4 조각으로 만든 뒤 두 재생목록을 비교했다. 실제 영상 바이트는 같으며 세그먼트 이름만 `.m4v`와 `.m4s`로 다르다. 외부 네트워크는 사용하지 않았다.

| 조건 | 결과 |
|---|---|
| fMP4 세그먼트 `.m4v` | 첨부 로그와 같은 확장자 불일치·첫 조각 실패 재현, macOS 종료 코드 183 |
| 같은 바이트의 세그먼트 `.m4s` | 1~3초 구간 처리 성공, 출력 2.000초·전체 디코딩 통과 |

검사 폴더: 프로젝트 상위 `outputs/range-hls-diagnosis-20261030/`. `reproduce.py`, `reproduction.json`, 합성 재생목록·조각·오류 로그를 보관했다. 원본 사용자 영상이나 서명 URL은 포함하지 않는다. 이 폴더는 앱 또는 GitHub 배포에 포함하지 않았다.

## 기존 검증의 사각지대

preview.6의 HTTPS 검사는 직접 MP4와 MPEG-TS `.ts` 기반 HLS를 사용했다. HTTPS 프로토콜·TLS 인증서 검증·해당 두 형식 검사는 유효하지만, fMP4 초기화 조각과 `.m4v` 영상 조각 조합은 포함하지 않았다. 따라서 CI 성공이 모든 치지직 HLS 형식의 성공을 보장하지 못했다. 이번 조합은 macOS 배포 바이너리에서 실패를 재현했으며 Windows 바이너리의 동일 합성 시험은 이번 점검에서는 실행하지 않았다.

## 수정 방향과 예외·영향

- 특정 VOD 번호·CDN·화질을 예외로 두지 않고, 실제 MP4로 판별된 HLS 조각에 한해 `.m4v`를 유효한 별칭으로 인정하는 공통 호환 패치를 검토한다.
- `allowed_extensions=ALL`만으로는 두 번째 형식 대조 실패가 해결되지 않는다. `extension_picky=0`은 확장자 허용 검사까지 생략하므로 전체 검사 해제를 해결책으로 사용하지 않는다.
- HTTPS 인증서 검증과 원격 프로토콜 제한, MP4 외 다른 형식의 기존 확장자 검사는 유지한다.
- 오류 안내에 형식·확장자 호환 문제를 구분하고 로그의 전체 경로를 제공한다. 서명된 URL은 화면에 복사하지 않는다.
- 다음 빌드의 macOS·Windows 실제 패키지에서 fMP4 `.m4v`와 `.m4s`, 초기화 조각, 쿼리 문자열이 있는 조각을 모두 검사한다. 정상 출력 길이·영상/오디오 전체 디코딩을 확인하고, 잘못된 형식과 허용하지 않은 확장자는 계속 거부하는지 확인한다.
- 기존 직접 MP4·TS HLS 수신과 TLS 인증서 거부 4종을 유지한다. 원본 및 기존 결과는 재작성하거나 삭제할 필요가 없다.

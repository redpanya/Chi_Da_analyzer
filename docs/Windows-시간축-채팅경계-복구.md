# Windows 영상 시간축·채팅 경계 복구

작성일: 2026-10-16. 원본과 이전 결과를 보존하며, 특정 VOD의 시각·제목·문장을 예외 처리하지 않는다.

## 영상 처리

기존에는 원본과 재생본의 컨테이너 표시 길이가 1초를 초과해 다르면 중단했다. 시작 시각을 0초로 정리한 조각형 MP4와 일반 MP4는 길이 표현이 달라질 수 있어 이 비교만으로 실제 누락을 구분할 수 없었다.

`media_timeline.py`에서 전체 패킷을 순차 확인한다. 각 영상·음성 트랙의 실제 첫 PTS·마지막 PTS+패킷 길이, 개수, 압축 내용의 SHA-256 누적값을 기록한다. 첫 기준점을 맞춘 뒤 각 트랙의 시작·끝을 비교한다. 기존 1초 범위 검사를 상대 시간 범위에 적용하며 허용치를 늘리지 않는다. 재인코딩 없는 복사에서는 패킷 개수와 압축 내용도 같아야 한다. 재인코딩에서는 내용 해시가 바뀌므로 트랙 구성·상대 시간 범위와 FFmpeg 처리를 검사한다. 모든 포맷에 `duration-start_time`을 일괄 적용하지 않는다.

패킷 출력은 크기가 제한된 큐로 읽으며 전체 패킷 목록을 메모리나 임시 텍스트 파일에 저장하지 않는다. 파일 경로·크기·수정 시각·검사 버전별 요약을 보관해 동일 파일의 재시도에 재사용한다. 검사 중 변경, 시각 불명, 실제 잘림, 다른 음성·영상, 트랙 손실은 완료 처리하지 않는다. 취소하면 자식 도구를 종료하고 완료 요약만 남긴다.

## 저장 자료 복구·보존

- `original.mp4`, 수신 식별 자료 `source.json`, 수신 후 `probe.json`이 있고 VOD·화질·크기가 일치하며 다운로드 부분 파일이 없으면 서버 재요청 없이 원본을 검사한다. 수신 완료 근거가 없는 부분 파일에는 기존 온라인 이어받기를 유지한다. 원본 크기·식별이 다르면 우회하지 않는다.
- 원본 전체 디코딩 검사는 유지한다. 장시간 영상은 재다운로드 없이도 이 검사와 첫 패킷 대조에 시간이 걸린다. 기존 파일이 있다는 이유만으로 즉시 완료시키지 않는다.
- 이전 `playback.mp4`·`playback.tmp.mp4`는 전체 압축 패킷 보존을 확인한 경우 원래 경로 그대로 재사용한다. 불일치 파일은 보존하고 새 ID의 재생본을 생성한다. 이전 재인코딩 결과는 압축 내용 대조로 인수할 수 없어 새 재생본을 만든다.
- 진단·검증 결과는 새 ID의 폴더에 기록하며 기존 원본 probe·검증 파일·로그를 덮어쓰지 않는다. 완료 프로젝트를 자동 변환하거나 기존 전사·교정·화자·요약을 재생성하지 않는다.
- 로컬 영상 가져오기의 재생본 길이 검사에도 같은 상대 시간 비교를 적용한다. 새 재생본을 쓰는 프로젝트의 길이는 검증한 재생본 기준으로 기록한다.

## 채팅 경계 처리

API의 다음 커서가 마지막 메시지의 밀리초와 같을 때 같은 시각의 나머지 메시지가 다음 페이지에서 제외될 수 있다. `chat_boundary.py`에서 수집 페이지와 경계 1ms 전 재조회 응답을 대조해 **그 경계 시각에서만** 누락 발생 횟수를 보완한다.

- 기존 경계 응답이 있으면 이를 읽고 없는 응답만 요청한다. 현재 서버의 새 상태와 역사적 전체 채팅을 확인했다고 표시하지 않는다.
- 전체 메시지 지문과 발송 시각·사용자·내용 기반 사건 식별을 함께 비교한다. 실제 동일 반복 메시지는 횟수만큼 유지한다. 프로필 변경 등으로 같은 사건의 표현만 바뀐 경우에는 중복으로 추가하지 않고 검증 필요 상태를 유지한다.
- 경계 밖 불일치, 안정적인 식별 정보 부족, 한 밀리초 200건 응답 한도, 페이지 역행·겹침은 자동 완료하지 않는다. 누락 경고를 단순 무시하지 않는다.
- 보완 자료는 SQLite와 새 내보내기에 시간순으로 합친다. 원본 수집 페이지·기존 경계 응답·이전 내보내기는 유지한다. 복구 근거와 건수는 새 `boundary-recovery.json`에 기록한다. 재시도해도 같은 메시지를 누적해서 추가하지 않는다.
- 기존 요약과 분석은 그대로 남으며, 새 채팅 내보내기를 선택하므로 기존 분석의 입력 변경 표시가 생길 수 있다. 사용자가 다시 분석하기 전에는 결과를 덮어쓰지 않는다.
- 중단·디스크 부족·손상 응답은 기존 선택 결과를 유지한다. 모든 새 내보내기가 만들어진 뒤 참조를 바꾼다. 화면에는 보완 건수, 남은 불일치·응답 한도 사유를 표시한다.

## 검증 기록

- 범용 복구 검사 7개 통과: 양수·음수 시작 이동, 20시간 시간 범위, 실제 손실·패킷 변경·음성 상대 이동 거부, 재인코딩 경계, 실제 반복 보존, 프로필 변경·경계 밖 누락 보류, 포화 응답 보류, 손상 경계 자료에서 기존 결과 유지, 재시도 중복 방지.
- 기존 저장·채팅·취소·API 검사 21개, 영상 검사 2개, 로컬 가져오기 검사 6개 통과. 이전 Windows 인코딩 회귀 검사도 macOS에서 5개 통과·Windows 전용 1개 건너뜀.
- macOS 개발 서버에서 시작 시각이 0이 아닌 조각형 MP4와 기존 임시 재생본을 준비하고 실제 가져오기 API로 오프라인 복구 → 원음 트랙 조회를 통과했다. 같은 API 흐름에서 저장된 경계 응답으로 채팅을 보완했고 기존 파일 해시가 유지됐다.
- 사용자 제공 13시간 VOD의 채팅 복사본을 네트워크 요청 금지 조건으로 실행했다. 90개 경계 응답을 재사용해 누락 1건을 보완하고 **17,802건·완료**를 확인했다. 기존 페이지·진단 파일 181개의 SHA-256이 같았다. 원래 Windows 보관함은 읽기만 했다.
- 실제 장시간 영상의 전체 패킷 대조 및 Windows 패키지 CI 결과는 확인 후 아래에 추가한다. 전체 전사·요약·GPU 추론 검증은 이번 수정 범위가 아니다.

## Windows 재시도 방법

이전 앱을 종료하고 수정 ZIP 전체를 새 폴더에 푼 뒤 같은 보관함과 모델 폴더를 선택한다. 해당 VOD에서 영상·채팅의 **다시 시도**를 누른다. 이전 원본·수신 후 검사 기록·경계 응답이 유효하면 새로 받지 않고 검사와 보완을 진행한다. 원본 또는 결과 파일을 직접 지우거나 상태 JSON을 완료로 바꿀 필요는 없다.

# macOS 배포본의 손상 경고 진단

작성일: 2026-10-16. 사용자 요청 범위는 원인 점검이다. 앱 코드·사용자 다운로드 파일·GitHub 배포본·시스템 보안 설정은 변경하지 않았다.

## 결론

사용자가 받은 앱에서는 번들 안의 `Contents/Resources/사용안내.md` 파일명이 서명 당시의 유니코드 조합형(NFC)에서 분해형(NFD)으로 달라져 코드 서명이 무효가 됐다. 화면에 보이는 한글과 파일 내용은 같지만 macOS 서명 검사는 이를 누락 파일과 추가 파일로 각각 판정한다. 이번 손상 경고의 직접 원인은 이 패키징 호환성 문제다.

별도로 현재 배포본은 임시 서명이며 Developer ID 서명·공증이 없다. 파일명 문제를 해결해도 인터넷에서 받은 앱의 Gatekeeper 허용까지 보장하지 않는다. 정상 서명의 별도 해제본도 Gatekeeper 평가에서는 거부됐다. 두 문제는 구분해서 해결해야 한다.

## 점검 대상과 증거

- 사용자 앱: `/Users/brightp/Downloads/package-macOS-arm64/치(지직) 다(시보기) 분석기.app`
- macOS: 27.0.1, 빌드 26A434.
- 앱 버전: 0.18.0, 번들 빌드 15, arm64, 최소 macOS 14.0.
- 비교 배포 ZIP: `v0.18.0-preview.4`의 `Chi_Da_analyzer-macOS-arm64.zip`.
- ZIP SHA-256: `a690f5eda2487bc9ce06e477dc54641494d29110cd63f6dcb997ec23c360ccc4`.
- 사용자 앱에는 Chrome이 남긴 `com.apple.quarantine` 속성이 있다. 이 속성이나 보안 설정을 제거·변경하지 않았다.

| 검사 | 결과 |
| --- | --- |
| 사용자 앱 `codesign --verify --deep --strict` | 실패: `a sealed resource is missing or invalid` |
| 구체적인 서명 오류 | `사용안내.md`가 추가·누락 파일로 동시에 표시됨 |
| 동일 ZIP을 `ditto`로 새로 해제한 앱 | 코드 서명 검사 통과 |
| 두 앱의 파일·링크 240개 비교 | 내용·권한·링크 대상 차이 없음 |
| 실제 파일명 비교 | `Contents/Resources/사용안내.md` 하나의 NFC/NFD 차이 |
| 서명 명세의 사용 안내 파일 내용 해시 | 사용자 파일의 내용과 일치 |
| 사용자 앱의 별도 복사본에서 파일명만 NFC로 복원 | 재서명 없이 코드 서명 검사 통과 |
| 사용자 앱의 Gatekeeper 평가 | 봉인된 리소스 누락·무효로 거부 |
| 서명이 정상인 별도 ZIP 해제본의 Gatekeeper 평가 | 거부. 임시 서명·TeamIdentifier 없음 |

복사본 실험은 `outputs/macos-gatekeeper-20261016/filename-check.app`에서만 수행했다. 실행 허용 예외를 만들거나 실제 보관함을 열지 않았다. 사용자 다운로드 파일의 내용이나 이름은 변경하지 않았다.

압축 해제 전후의 이름 변화가 직접 확인됐지만 사용자가 사용한 해제 도구의 종류는 확정하지 않았다. 특정 해제 프로그램만의 버그로 단정하지 않는다. Apple도 같은 종류의 유니코드 정규화에 따른 서명 손상을 설명하며 번들 내부 파일에 ASCII 이름 사용을 권고한다.

## 기존 검증에서 놓친 점

`packaging/release/assemble.py`는 한국어 문서를 번들 안의 `사용안내.md`로 복사하고 임시 서명 및 서명 검사를 한다. 이후 `archive_release.py`에서 ZIP을 만든다. 최종 ZIP을 사용자 방식으로 다시 해제한 뒤 서명을 검사하는 단계는 없다.

`packaging/release/smoke.py`의 macOS 검사는 앱의 내부 `archive-backend`를 직접 실행한다. 미디어·API 기능 검증은 유효하지만, Finder/LaunchServices로 인터넷 다운로드 앱을 처음 여는 검증은 아니다. 따라서 이전 Windows·macOS 패키지 검사 통과 기록을 일반 사용자 환경의 macOS 첫 실행 보장으로 해석하면 안 된다.

## 수정 방향과 영향

1. macOS 번들 내부의 안내 파일을 `README.ko.md`처럼 ASCII 파일명으로 저장한다. 본문·앱 표시 이름은 한국어로 유지한다. 현재 코드에서 이 파일을 여는 런타임 참조는 발견되지 않았다. Windows 파일명이나 기존 보관함·결과를 바꿀 필요는 없다.
2. 최종 ZIP 재해제 후 `codesign --verify --deep --strict`를 실행하고 번들 내부 비ASCII 파일명을 점검한다. 단순히 `ditto` 왕복만 통과하면 이번 현상을 놓칠 수 있으므로, 파일명이 정규화되는 해제 경로에 해당하는 회귀 검사도 포함한다. 파일명 충돌·링크 변경은 실패로 처리한다.
3. 내부 서버 검사와 실제 앱 실행·Gatekeeper 검사를 별도 결과로 기록한다. 임시 서명 빌드가 Gatekeeper에서 거부되면 배포 가능 검사에 통과한 것처럼 표시하지 않는다.
4. 일반 사용자에게 보안 설정 변경 없이 배포하려면 Developer ID 서명, 공증, 결과 티켓 확인과 실제 다운로드 후 첫 실행 검사가 필요하다. 인증서·공증 자격 정보가 준비되지 않은 상태에서 완료로 표시하지 않는다. 로컬 임시 서명으로 해당 절차를 대신할 수 없다.

기존 다운로드 앱에 덮어쓰거나 임의로 재서명하는 방식은 진단 증거를 바꾸므로 이번 점검에서는 수행하지 않았다. 향후 수정 빌드도 기존 버전과 보관함을 유지하고 새 배포본으로 제공해야 한다. 파일명만 수정한 빌드와 공증까지 마친 빌드의 검증 범위를 분리해 안내한다.

## 자료와 남은 범위

로컬 점검 자료는 작업 공간의 `outputs/macos-gatekeeper-20261016/`에 보관했다.

- `signatures.json`: 두 앱의 서명·번들 정보·속성.
- `bundle-comparison.json`: 전체 파일·링크 대조와 파일명 차이.
- `filename-proof.json`: 별도 복사본의 파일명 수정 전후 서명 검사.
- `gatekeeper.json`: 시스템 정책 평가. 샌드박스 안의 내부 오류 대신 권한이 허용된 읽기 전용 평가 결과를 기록했다.

앱 기능 전체 재검증, 수정 빌드 생성, GitHub 업로드, 인증서 등록·공증, 사용자 앱 실행 허용은 하지 않았다.

# macOS exFAT 채팅 DB 쓰기 오류 진단

## 요청과 범위

2026-10-18, macOS에서 가져오기의 채팅 작업에 `attempt to write a readonly database`가 표시되는 원인을 조사했다. 대상은 `<VOD 보관함>/vod-15655103`이다. 기존 자료를 읽어 진단하고 별도 임시 자료로 재현·복구 가능성을 검사했다. 앱 코드 수정, 패키징, 배포 및 실제 프로젝트 상태 변경은 하지 않았다.

## 확인된 원인

외장 USB 볼륨은 exFAT이며 미디어·볼륨 모두 읽기 전용이 아니다. 실행 사용자에게 해당 폴더와 DB의 쓰기 권한이 있고 여유 공간은 약 311 GB였다. 권한을 풀거나 관리자 권한으로 실행해야 하는 문제로 확인되지 않았다.

배포본 `v0.18.1-preview.1`의 `_sqlite3` 확장 모듈에는 SQLite 3.45.1이 포함되어 있다. 해당 모듈을 그대로 로드해 새 임시 DB를 만들고, 실제 채팅 내보내기처럼 테이블 생성 → 결과 파일 생성 → 첫 행 삽입을 수행했다.

| 환경 | SQLite | 결과 |
| --- | --- | --- |
| 내장 디스크 `/private/tmp` | 배포본의 3.45.1 | 정상 삽입·커밋 |
| 외장 exFAT 볼륨 | 배포본의 3.45.1 | `SQLITE_READONLY_DBMOVED`, 코드 1032 |
| 내장 디스크 `/private/tmp` | 개발 환경의 3.53.4 | 정상 삽입·커밋 |
| 동일 외장 exFAT 볼륨 | 개발 환경의 3.53.4 | 정상 삽입·커밋 |

배포본 엔진의 exFAT 검사에서는 파일을 직접 이동하지 않았음에도 DB를 처음 열 때의 inode가 `18446744073709545006`에서 테이블 생성 뒤 `8659`로 바뀌었다. 이어지는 첫 삽입이 파일 이동 보호 검사에 걸렸다. 최신 개발 환경에서는 같은 검사 중 inode가 유지됐다. 이는 해당 Mac·외장 볼륨·배포 엔진 조합에서 직접 재현한 결과이며, 모든 exFAT 장치나 SQLite 버전의 동작을 단정하지 않는다.

[SQLite 공식 오류 설명](https://www.sqlite.org/rescode.html#readonly_dbmoved)에 따르면 `SQLITE_READONLY_DBMOVED`는 열린 DB의 이동으로 저널이 잘못 연결되는 것을 막는 오류다. 일반 파일 권한 오류와 같은 메시지가 보일 수 있지만 이번 재현의 확장 오류 코드는 1032였다.

## 기존 자료 상태

- 채팅 원본 90페이지가 저장돼 있고 수집 커서는 종료 상태였다. 원본 페이지의 메시지 수는 17,801건이었다.
- 최근 실패한 내보내기 4개 모두 `counts` 테이블 생성까지 성공했으나 저장된 행은 0개였다. 첫 채팅 문장까지 작성된 작은 출력 파일이 남아 있었다. 관찰된 실패 지점이 위 재현과 일치한다.
- 과거 Windows에서 생성된 내보내기와 검사 기록도 남아 있다. 최근 실패 상태가 과거 결과 파일 자체의 삭제·손상을 뜻하지 않는다.
- 원본·부분 출력·기존 내보내기는 삭제하거나 변경하지 않았다. 진단에서 새로 생성한 임시 폴더만 정리했다.

## 재다운로드 없는 복구 검증

원본 90페이지, 저장된 경계 응답 90개, 프로젝트 메타데이터를 내장 디스크의 별도 임시 폴더로 복사했다. 실제 배포본 SQLite 3.45.1을 사용해 현재 `chat.collect`를 실행했으며 모든 네트워크 채팅 요청은 예외를 발생시키도록 차단했다.

- 결과: `complete`, 채팅 **17,802건**.
- 저장된 경계 응답 90개 재사용, 네트워크 요청 0회, 경계 누락 1건 보완.
- 처리 시간: 17.77초. 실제 영상 다운로드나 전체 분석의 소요 시간을 뜻하지 않는다.
- 원래 위치의 입력 파일 181개는 실행 전후 SHA-256이 같았다.
- 검증 복사본은 임시 자료이므로 실행 후 정리했다. 사용자의 실제 VOD는 아직 오류 상태 그대로이며 복구 완료로 표시하지 않았다.

## 해결 방향과 제한

즉시 사용할 수 있는 우회는 앱의 작업을 끝내고 종료한 뒤, 기존 `vod-15655103` 폴더를 쓰기 가능한 내장 디스크 보관함에 **복사**하고 그 상위 보관함을 선택해 채팅을 재시도하는 것이다. 새 빈 보관함만 선택하면 기존 자료가 자동 이동되는 것은 아니다. 영상까지 포함한 폴더 복사는 크기만큼 추가 저장 공간이 필요하다. 원래 폴더는 복구 확인 전 삭제하지 않는다.

앱 차원의 개선은 채팅 대조용 SQLite 작업 파일을 내장 디스크의 임시 작업 위치에서 다루고, 보관함에는 닫힌 결과 파일을 저장하는 방식 또는 호환성이 확인된 SQLite를 배포하는 방식을 검토할 수 있다. 전자는 작업 공간 부족·취소·정상 종료·재시작 시 원본에서 재구성하는 처리와 완료 결과 참조의 마지막 갱신이 필요하다. 후자는 네이티브 모듈 의존성·서명·macOS/Windows 패키지 검사를 다시 해야 한다. DB 파일 이동 보호나 저널 기능을 비활성화해 오류만 우회해서는 안 된다.

이번 조사만으로 보관함 이동, SQLite 교체, 실제 사용자 프로젝트 복구나 수정 빌드가 완료됐다고 간주하지 않는다. 기존 패키지 검사는 내장 디스크에서 수행되어 이 외장 exFAT 조건을 포괄하지 못했다.
